# 接口主流程识别与设计

> **只生成符合业务的主流程接口用例**：读 Controller/DTO 真实契约，串成端到端 HTTP 链路。  
> 缺省数据用 **mock 数据** 辅助，不追求全端点、全校验场景穷举。

---

## 1. 交付目标

| 维度 | 目标 |
|------|------|
| 用例数量 | **不设上限**；含 1 条登录 + 每条主流程至少 1 条 WF 用例 |
| 覆盖范围 | **核心业务 API 主路径**（happy path + 必要鉴权） |
| 请求体 | 字段名与 DTO 一致；缺省值用 mock / `{{timestamp}}` |
| 链路 | 登录 extract → 创建 extract → 下游 `{{var}}` 引用 |

**验收口径**：每条识别出的主流程有可执行用例，请求/断言与源码一致。

---

## 2. 主流程是什么

主流程 = 完成一项**核心业务目标**所需的最短 API 调用序列（以 happy path 为主）。

| 类型 | 示例 | 识别信号（源码） |
|------|------|------------------|
| 会话入口 | 登录获取 token | `POST /auth/login` + token 响应字段 |
| 资源生命周期 | 创建 → 查询 → 更新 → 删除 | POST/GET/PUT/DELETE 同资源路径 |
| 状态流转 | 提交 → 审核 → 发布 | PATCH/PUT 改 status + Service 状态机 |
| 跨模块串联 | 创建 A → B 引用 A | B 的 DTO 含 A 的外键/id |
| 关键交易 | 下单 → 支付回调 | 多 Controller 协作 + chainHints |

**不是主流程**（默认不写）：

- 每个 `@NotBlank` 单独一条校验失败用例
- 分页/排序/筛选组合
- 401/403 的每种变体（登录主流程已覆盖 token 即可）
- 重复提交、并发、安全扫描类用例
- Actuator、静态资源、配置类 GET

## 3. 识别步骤

### 3.1 读输入

1. `project-analysis`：`modules[].endpoints`、`auth`、`chainHints`
2. **主流程涉及**的 Controller 方法 + DTO（非全量逐端点扫描）
3. `GlobalExceptionHandler`：成功/失败的 `status` + `body.code` 约定

### 3.2 从 chainHints 与业务动词归纳

优先读 `chainHints.candidateChains`，再读 Controller 中：

- `POST` 创建类、`PUT/PATCH` 更新类、`DELETE` 删除类
- 动作型映射：`/submit`、`/approve`、`/publish`

### 3.3 写入 mainFlowInventory

```json
{
  "id": "FLOW-ORDERS-001",
  "name": "订单创建到提交",
  "module": "orders",
  "priority": "P0",
  "businessGoal": "用户创建订单并提交审核",
  "endpointSequence": [
    "POST /api/v1/orders",
    "PUT /api/v1/orders/{id}/submit"
  ],
  "evidence": [
    "OrderController.create",
    "OrderController.submit"
  ],
  "suggestedCaseIds": ["TC-API-WF-ORDERS-001", "TC-API-WF-ORDERS-002"],
  "chainVars": ["token", "orderId"],
  "mockHints": ["customerId 可用 mockData.customerId"]
}
```

### 3.4 数量原则

- **不设人为上限**：凡从源码识别出的真实主流程均写入 `mainFlowInventory`
- 仅排除 §2「不是主流程」的子功能（校验失败、分页筛选组合等）
- 小型项目可能只有 2～3 条，大型项目可能 20+ 条，均以实际业务为准

## 4. 用例编写规则

### 4.1 结构

- **登录**：1 条 `TC-API-AUTH-001`，`produces: ["token"]`
- **主流程**：每条流程 1～N 条 `TC-API-WF-*`（多步链路拆成依赖链，同一 `flowRef`）

用 `flowRef: "FLOW-ORDERS-001"` 追溯主流程（类似 UI 的 `featureRefs`）。

### 4.2 每条用例只测一个 HTTP 请求

保持现有结构：`request` + `assertions` + `extract`。多步主流程 = 多条 WF 用例 + `dependsOnCases`。

### 4.3 Mock 数据（辅助测试）

当上游暂未产出、或字段需固定种子值时，使用 mock：

**元信息级**（全局 fixtures）：

```json
{
  "mockData": {
    "customerId": "MOCK-CUST-001",
    "productSku": "SKU-DEMO-01",
    "warehouseCode": "WH-01"
  }
}
```

**用例级**（仅该用例缺省填充，不覆盖已有变量）：

```json
{
  "mockData": { "quantity": 1, "currency": "CNY" },
  "request": {
    "body": {
      "customerId": "{{customerId}}",
      "sku": "{{productSku}}",
      "qty": "{{quantity}}"
    }
  }
}
```

Mock 数据规则：

| 规则 | 说明 |
|------|------|
| 来源 | 从 DTO 字段类型推断合理值；外键优先用种子/Mock id |
| 命名 | 变量名小驼峰，与 body 字段对应 |
| 唯一性 | 创建类仍用 `AUTO-{{timestamp}}` 避免冲突 |
| 标注 | `mainFlowInventory[].mockHints` 说明哪些字段用了 mock |
| 禁止 | 臆造 DTO 中不存在的字段名 |

执行器启动时将 `meta.mockData` 注入变量池；用例级 `mockData` 在当次请求前补全缺失变量。

### 4.4 断言

主流程用例至少：

```json
{ "field": "status", "operator": "eq", "expected": 200 },
{ "field": "body.code", "operator": "eq", "expected": 0 }
```

创建类额外断言 `body.data.id` exists 并 `extract`。

## 6. 验收清单

- [ ] `mainFlowInventory` 已填写，`evidence` 来自 Controller/DTO
- [ ] `mainFlowCoveragePercent` = 100%
- [ ] 请求体字段与 DTO 一致
- [ ] 鉴权头使用 `{{token}}`；登录用 `{{username}}/{{password}}`
- [ ] mock 字段在 `mockData` 或 `mockHints` 中有说明
- [ ] 链路 `dependsOnCases` / `produces` / `consumes` 可解析

## 7. 反模式

- 每个端点机械 4 条 H/V/A/E
- 未读 DTO 写 request body
- 硬编码 `id=1`、写死 token
- mock 字段名与 DTO 不一致
- 为凑 endpointCoverage 补无关 GET
