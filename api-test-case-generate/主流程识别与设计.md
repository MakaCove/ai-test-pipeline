# 接口主流程识别与设计

> **只生成符合业务的主流程接口用例**：读 Controller/DTO 真实契约，串成端到端 HTTP 链路。
> 缺省数据用 **mock 数据** 辅助，不追求全端点、全校验场景穷举。

---

## 1. 交付目标

| 维度 | 目标 |
|------|------|
| 用例数量 | **不设上限**；含登录 + 每条主流程至少 1 条用例 |
| 覆盖范围 | **核心业务 API 主路径**（happy path + 必要鉴权） |
| 请求体 | 字段名与 DTO 一致；缺省值用 mock / `{{timestamp}}` |
| 链路 | 登录 extract → 创建 extract → 下游 `{{var}}` 引用 |
| 用例 ID | 统一 `TC-API-{MODULE}-{序号}`（登录为 `TC-API-AUTH-*`） |

**验收口径**：每条识别出的主流程有可执行用例，请求/断言与源码一致。

---

## 2. 主流程是什么

主流程 = 完成一项**核心业务目标**所需的最短 API 调用序列（以 happy path 为主）。

| 类型 | 示例 | 识别信号（源码） |
|------|------|------------------|
| 会话入口 | 登录获取 token | `POST /auth/login` + token 响应字段 |
| 资源生命周期 | 创建 → 查询 → 更新 → 删除 | POST/GET/PUT/DELETE 同资源路径 |
| 状态流转 | 提交 → 审核 → 发布 | PATCH/PUT 改 status + Service 状态机 |
| 跨模块串联 | 创建 A → B 引用 A | B 的 DTO 含 A 的外键/id |
| 关键交易 | 下单 → 支付回调 | 多 Controller 协作 + chainHints |

**不是主流程**（默认不写）：

- 每个 `@NotBlank` 单独一条校验失败用例
- 分页/排序/筛选组合
- 401/403 的每种变体（登录主流程已覆盖 token 即可）
- 重复提交、并发、安全扫描类用例
- Actuator、静态资源、配置类 GET

## 3. 识别步骤

### 3.1 读输入

1. `project-analysis`：`modules[].endpoints`、`auth`、`chainHints`、**`stateHints`**、**`mainFlowCandidates`**、**`crossModuleRefs`**
2. **主流程涉及**的 Controller 方法 + DTO（非全量逐端点扫描）
3. `GlobalExceptionHandler`：成功/失败的 `status` + `body.code` 约定

### 3.2 优先确认 mainFlowCandidates

`mainFlowCandidates[]` 由 analyzer 阶段预标注，逐条处理：

- `confidence: high`：直接确认，写入 `mainFlowInventory`
- `confidence: medium`：读源码核对，确认后写入
- `confidence: low`：评估业务价值，合理则写入

### 3.3 从 chainHints / stateHints / crossModuleRefs 补充

- `chainHints.candidateChains`：补全资源生命周期
- `stateHints[].transitions`：补全状态流转主流程
- `crossModuleRefs`：补全跨模块串联主流程

### 3.4 写入 mainFlowInventory

```json
{
  "id": "FLOW-ORDERS-001",
  "name": "订单创建到提交",
  "module": "orders",
  "priority": "P0",
  "businessGoal": "用户创建订单并提交审核",
  "endpointSequence": ["POST /api/v1/orders", "PUT /api/v1/orders/{id}/submit"],
  "evidence": ["OrderController.create", "OrderController.submit"],
  "suggestedCaseIds": ["TC-API-ORDERS-001", "TC-API-ORDERS-002"],
  "chainVars": ["token", "orderId"],
  "mockHints": ["customerId 可用 mockData.customerId"],
  "confidence": "high"
}
```

### 3.5 数量原则

- **不设人为上限**：凡从源码识别出的真实主流程均写入
- 仅排除 §2「不是主流程」的子功能
- 小型项目可能只有 2～3 条，大型项目可能 20+ 条

## 4. 用例编写规则

### 4.1 结构

- **登录**：1 条 `TC-API-AUTH-001`，`trace.produces: ["token"]`
- **主流程**：每条流程 1～N 条 `TC-API-{模块}-{序号}`（多步链路拆成依赖链，同一 `trace.flowRefs`）

### 4.2 每条用例只测一个 HTTP 请求

保持现有结构：`request` + `assertions` + `extract`。多步主流程 = 多条用例 + `trace.dependsOn`。

### 4.3 trace 分组（链路字段）

所有链路字段统一放在 `trace` 对象中：

```json
{
  "id": "TC-API-ORDERS-001",
  "title": "创建订单",
  "module": "orders",
  "priority": "P0",
  "trace": {
    "flowRefs": ["FLOW-ORDERS-001"],
    "dependsOn": ["TC-API-AUTH-001"],
    "produces": ["orderId"],
    "consumes": ["token"]
  },
  "request": { "..." : "..." },
  "assertions": ["..."],
  "extract": { "orderId": "body.data.id" }
}
```

### 4.4 Mock 数据（辅助测试）

**元信息级**（全局 fixtures）：

```json
"mockData": { "customerId": "MOCK-CUST-001", "productSku": "SKU-DEMO-01" }
```

**用例级**（仅该用例缺省填充）：

```json
{
  "mockData": { "quantity": 1 },
  "request": { "body": { "customerId": "{{customerId}}", "qty": "{{quantity}}" } }
}
```

Mock 规则：字段名与 DTO 一致；外键用种子/Mock id；创建唯一字段用 `AUTO-{{timestamp}}`；在 `mockHints` 标注。

### 4.5 断言

主流程用例至少：

```json
{ "field": "status", "operator": "eq", "expected": 200 },
{ "field": "body.code", "operator": "eq", "expected": 0 }
```

创建类额外断言 `body.data.id` exists 并 `extract`。

## 5. 四维度交叉检查（强制 · 防止遗漏）

识别完主流程后，必须逐项核对，未覆盖项必须写明原因：

```
□ 维度 A：模块生命周期
  对每个模块：POST 创建 / GET 查询 / PUT 更新 / DELETE 删除
  是否都有对应主流程？（无创建操作的模块可说明）

□ 维度 B：chainHints 覆盖
  candidateChains 每条是否都有对应 FLOW？

□ 维度 C：stateHints 覆盖
  每条 transitions 是否都有对应 FLOW？（状态机不应遗漏）

□ 维度 D：crossModuleRefs 覆盖
  跨模块外键引用是否都有跨模块 FLOW？
```

未覆盖的维度必须在 `scanLimitations` 或 `coverage.uncoveredMainFlows` 中说明原因（如"该模块无创建操作"/"该状态机不在主流程范围"）。

## 7. 验收清单

- [ ] `mainFlowInventory` 已填写，`evidence` 来自 Controller/DTO
- [ ] `mainFlowCoveragePercent` = 100%
- [ ] 请求体字段与 DTO 一致
- [ ] 鉴权头使用 `{{token}}`；登录用 `{{username}}/{{password}}`
- [ ] mock 字段在 `mockData` 或 `mockHints` 中有说明
- [ ] `trace.dependsOn` / `trace.produces` / `trace.consumes` 可解析
- [ ] 四维度交叉检查已完成，未覆盖项有说明

## 8. 反模式

- 每个端点机械 4 条 H/V/A/E
- 未读 DTO 写 request body
- 硬编码 `id=1`、写死 token
- mock 字段名与 DTO 不一致
- 为凑 endpointCoverage 补无关 GET
- 仅凭"灵感"归纳主流程，不做交叉检查
