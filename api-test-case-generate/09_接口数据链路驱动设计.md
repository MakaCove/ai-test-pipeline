# 09 — 数据链路驱动设计（接口通用）

> 目标：接口用例不只是“单请求覆盖”，而是“契约覆盖 + 业务链路覆盖”。  
> 原则：**凡是存在上游产出、下游消费关系的端点，都应形成链路表达。**

---

## 1. 适用范围（不限登录/CRUD）

满足任一条件即视为“可串联场景”：

- 下游端点依赖上游端点产出的业务主键/外键（如 `projectId`、`taskId`、`versionId`）
- 下游端点依赖上游鉴权上下文（`token`、租户、角色）
- 操作具备生命周期（create → update/action → delete/archive）
- 状态类端点具备前置状态（仅在某状态可触发）

---

## 2. 识别步骤（生成阶段必须执行）

对每个 `endpointContracts` 项分析：

1. 是否生产数据（create/login/start 等）？
2. 是否消费数据（get by id/update/delete/action/filter）？
3. 消费数据来源于哪一条上游用例？

输出到用例字段：

- `contractRef` / `scenarioRef`（契约追溯）
- `dependsOnCases`（上游用例依赖）
- `produces` / `consumes`（变量产出与消费）
- `extract`（运行时提取路径，执行器实际使用）

---

## 3. 编排模板（领域无关）

`认证` → `创建` → `查询` → `修改/动作` → `删除/清理`

规则：

- 上游生产者在前，下游消费者在后
- 消费者必须能追溯到上游（`dependsOnCases`）
- `consumes` 变量应在上游 `produces` 或本用例 `extract` 链中可解析

---

## 4. 字段约定（向后兼容）

以下字段为可选增强，不破坏 `api-case/v1`：

```json
{
  "id": "TC-API-WF-001",
  "contractRefs": ["CTR-AUTH-POST-001", "CTR-ORDERS-POST-001"],
  "scenarioRef": "SCN-WF-CREATE-ORDER",
  "dependsOnCases": ["TC-API-AUTH-001", "TC-API-ORDERS-001"],
  "produces": ["token", "orderId"],
  "consumes": ["token", "orderId"],
  "extract": {
    "token": "body.data.token",
    "orderId": "body.data.id"
  }
}
```

---

## 5. 验收要点（链路维度）

- [ ] 可串联场景已识别，不仅限登录/CRUD
- [ ] 链路用例有明确上游依赖（`dependsOnCases`）
- [ ] `consumes` 变量可在上游 `produces` 或当前 `extract` 中找到来源
- [ ] destructive 行为置后或隔离，避免链路污染
- [ ] 推荐填写 `coverage.flowChains` 链路覆盖统计

---

## 6. 反模式

1. 把有依赖关系的端点写成互不关联用例
2. workflow 只写标题，不写变量产出/消费
3. 下游请求继续写死 `id=1`，绕过上游产出
4. `dependsOnCases` 指向不存在的用例 id
