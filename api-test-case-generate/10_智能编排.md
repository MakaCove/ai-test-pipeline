# 10 — 智能编排（接口用例 · 通用）

> **适用任意 REST 项目**，不绑定具体业务域、路径前缀或生成脚本。  
> 目标：消除执行期「变量缺失 / 会话吊销 / 依赖倒置」导致的跳过与级联失败。  
> 原则：**先产出、后消费；鉴权引导置顶；破坏性操作置后；编排由契约语义驱动，非模块编号驱动。**

与 [09_接口数据链路驱动设计.md](09_接口数据链路驱动设计.md) 的关系：

- **09**：识别「谁生产、谁消费」（链路图）
- **10**：把链路图落实为 `dependsOnCases` / `executionOrder` 等可执行编排（本文件）

---

## 1. 何时必须编排

在**所有契约场景用例编写完成**、**写入 JSON 之前**，Agent 必须执行本章流程。

触发信号（满足任一即须编排）：

| 信号 | 示例 |
|------|------|
| 路径含路径参数 | `GET /api/v1/orders/{orderId}` → 消费 `orderId` |
| 请求体/头含模板变量 | `Authorization: Bearer {{token}}`、`"customerId": "{{customerId}}"` |
| `project-analysis.chainHints` 存在 | `producerEndpoints` → `consumerEndpoints` |
| 端点语义为会话破坏性 | logout、改密、吊销 token、切换租户 |
| 存在跨端点 workflow 用例 | 须与单端点用例顺序协调 |

---

## 2. 输入（项目无关）

从以下来源读取，**禁止硬编码本项目 id 或路径**：

| 输入 | 用途 |
|------|------|
| `coverage.endpointContracts[]` | 方法、path、pathParams、requiresAuth、scenarios |
| `project-analysis.auth` | 测试账号、`publicPaths`、token 头格式 |
| `project-analysis.chainHints.candidateChains[]` | 跨模块生产者→消费者候选 |
| 已草稿化的用例数组 | `request`、`extract`、`produces`、`scenarioRef` |

---

## 3. 变量分类（通用）

编排前先将变量归类：

| 类型 | 命名特征 | 编排策略 |
|------|----------|----------|
| **系统变量** | `username`、`password`、`timestamp`、`tenantCode` | 由执行器/环境注入，**不**建立 `dependsOnCases` |
| **会话变量** | `token`、`accessToken`、`sessionId` | 由**登录类 happy 用例**生产；鉴权请求须消费 |
| **业务主键** | `{resource}Id`、`{resource}Code` | 由对应资源 **POST/create happy** 用例 `extract` |
| **派生/展示名** | `{resource}Name`、`displayName` | 由 UI 填表 `saveAs` 或创建响应字段提取 |
| **隔离会话变量** | 注册/访客登录产出的 token | **不得**与主会话共用变量名（见 §7） |

扫描规则：在 `request.path`、`request.headers`、`request.body`（递归）中匹配 `\{\{(\w+)\}\}`。

---

## 4. 生产者识别（从契约语义推断）

对每个用例，若满足以下条件则登记为**变量生产者**：

```
IF scenarioRef 为 happy / workflow 主成功场景
AND (
  存在 extract 映射
  OR method 为 POST/PATCH 且响应 successFields 含 id
  OR endpoint 语义为 login/sign-in/authenticate 且响应含 token
)
THEN 将该用例 id 登记为 produces[] 中各变量的生产者
```

**同变量多生产者时**，优选：

1. `scenarioRef === SCN-HAPPY`（或契约清单中 type=happy）
2. HTTP method 为 POST 的创建类
3. `executionTier` 更小者

**禁止**：写死 `dependsOnCases: ["TC-API-XXX-001"]`；必须指向**实际生产者用例 id**。

### 4.1 结合 chainHints

对 `chainHints.candidateChains[]` 每一项：

1. 在已生成用例中，用 `endpointKey` 或 `description` 匹配 `producerEndpoints[]`
2. 将 `suggestedVars[]` 绑定到匹配到的 happy 用例 id
3. 对 `consumerEndpoints[]` 对应用例补 `dependsOnCases` + `consumes`

chainHints 为**候选**；与契约扫描冲突时，以**契约 path/body 实际引用**为准。

---

## 5. 消费者识别与依赖补全

对每个用例：

1. 扫描所有模板变量（§3）
2. 对每个**非系统变量** `v`：
   - 若生产者索引存在 `v` → 将生产者 id 加入 `dependsOnCases`
   - 将 `v` 加入 `consumes`
3. 若 `requiresAuth === true` 且非 `SCN-A-NOAUTH` 类场景：
   - 将登录 happy 用例 id 置于 `dependsOnCases` 首位
   - `consumes` 含 `token`（或项目实际会话变量名）

**notFound / 业务异常**场景若使用占位 id（如 `999999`），**不**强制依赖创建用例。

---

## 6. executionTier（通用分层）

为每条用例赋值整数 tier（越小越先执行）：

| tier | 键名 | 判定规则（满足任一） |
|------|------|----------------------|
| 0 | `login-bootstrap` | 登录/sign-in happy，产出主会话 token |
| 1 | `session-guard` | 未登录访问受保护资源类（仅鉴权专项） |
| 2 | `resource-create` | POST create happy 且 `produces` 含业务 id |
| 3 | `resource-read` | GET 列表/详情 happy |
| 4 | `resource-update` | PUT/PATCH happy |
| 5 | `resource-action` | POST 动作（publish、approve、submit 等非 CRUD 创建） |
| 6 | `validation-negative` | 参数校验失败场景 |
| 7 | `auth-negative` | 无 token / 无效 token |
| 10 | `default` | 其他 |
| 80 | `resource-delete` | DELETE happy |
| 90 | `auth-destructive` | 登出、改密、吊销会话等 happy |
| 99 | `workflow` | `request.method === "WORKFLOW"` |

---

## 7. sessionImpact（会话破坏性）

对语义上会**使当前会话失效**的 happy 用例标注：

```json
"sessionImpact": "invalidate"
```

识别方式（读 Controller 注释 / 方法名 / 路径，**非硬编码路径表**）：

- logout、sign-out、revoke
- change-password、reset-password（修改当前用户密码）
- switch-user、impersonate 结束

标注后：

- `executionTier` 强制为 `90`
- 执行器应在该用例后**重建会话**（重新跑登录 bootstrap）

### 7.1 注册 token 隔离

注册 happy 若也返回 token，须：

```json
"extract": { "registerToken": "body.data.token" },
"produces": ["registerToken"]
```

**不得**使用 `produces: ["token"]` 覆盖主会话变量。

---

## 8. 拓扑排序与 executionOrder

在 tier 粗排基础上，按 `dependsOnCases` 做拓扑排序：

```
1. 构建有向图：dep → case
2. 入度为 0 的节点入队；同层按 (executionTier, module, id) 排序
3. 出队时写入 executionOrder = 1..N
4. 若存在环：打破环（移除低优先级场景的依赖边）并记录到 orchestration.warnings
```

**最终数组顺序**应与 `executionOrder` 一致（写入 JSON 前重排用例对象）。

---

## 9. 输出字段

### 9.1 用例级（每条）

| 字段 | 必填 | 说明 |
|------|------|------|
| `dependsOnCases` | 条件 | 上游用例 id 数组 |
| `produces` | 条件 | 本用例产出的变量名 |
| `consumes` | 条件 | 本用例消费的变量名 |
| `extract` | 条件 | 响应提取路径 |
| `executionTier` | ✅ | §6 分层值 |
| `executionOrder` | ✅ | 全文件内 1…N |
| `sessionImpact` | 条件 | 仅 `invalidate` |

### 9.2 元信息 `coverage.orchestration`

```json
{
  "strategy": "smart-orchestration-v1",
  "kind": "api",
  "totalCases": 120,
  "casesWithChainFields": 95,
  "dependenciesWired": 210,
  "producerVariables": ["token", "orderId", "customerId"],
  "loginBootstrapCaseId": "TC-API-AUTH-001",
  "executionTiers": { "login-bootstrap": 0, "resource-create": 2 },
  "warnings": []
}
```

`loginBootstrapCaseId` 填写**本项目**登录 happy 用例的真实 id，非固定字符串。

## 10. Agent 执行清单（逐步）

```
- [ ] A. 从 endpointContracts 列出所有 pathParams 与 body 外键字段
- [ ] B. 标记生产者端点（login/create/start）与消费者端点（get-by-id/update/delete/action）
- [ ] C. 合并 chainHints，绘制链路图（可 Markdown mermaid）
- [ ] D. 为每条 happy/create 用例填写 extract + produces
- [ ] E. 扫描消费者用例，补 dependsOnCases + consumes
- [ ] F. 标注 sessionImpact；注册 token 隔离
- [ ] G. 赋值 executionTier
- [ ] H. 拓扑排序，写入 executionOrder，重排 JSON 数组
- [ ] I. 写入 coverage.orchestration
- [ ] J. 执行 §11 验收
```

---

## 11. 验收要点

- [ ] 登录 happy 的 `executionOrder === 1`（或 tier=0 且无前序依赖）
- [ ] 任意含 `{{orderId}}` 的用例，其 `dependsOnCases` 含**创建 order 的 happy 用例 id**
- [ ] 所有 `sessionImpact: invalidate` 的 happy 用例 `executionOrder` 位于后 10%
- [ ] `dependsOnCases` 中每个 id 在文件内存在
- [ ] `consumes` 中每个变量在生产者 `produces` 或系统变量集中可解析
- [ ] 无可串联场景时 `dependenciesWired` 可为 0，但仍须有 `executionOrder`

---

## 12. 反模式

| 反模式 | 正确做法 |
|--------|----------|
| 按 `TC-API-{MODULE}-001` 猜测依赖 | 按生产者索引指向真实 happy 用例 |
| 全文件按 module 字母序 | tier + 拓扑排序 |
| 注册覆盖 `token` | 独立 `registerToken` |
| 登出/改密插在创建用例前 | tier=90 + 置后 |
| 只写 `consumes` 不写 `dependsOnCases` | 两者成对补全 |
| 引用 chainHints 但不核对 path 模板 | 以 request 内实际 `{{var}}` 为准 |

---

## 13. 示例（电商域，非特定项目）

```json
{
  "id": "TC-API-ORDERS-004",
  "contractRef": "CTR-ORDERS-GET-002",
  "scenarioRef": "SCN-HAPPY",
  "request": {
    "method": "GET",
    "path": "/api/v1/orders/{{orderId}}",
    "headers": { "Authorization": "Bearer {{token}}" }
  },
  "dependsOnCases": ["TC-API-AUTH-002", "TC-API-ORDERS-001"],
  "consumes": ["token", "orderId"],
  "executionTier": 3,
  "executionOrder": 15
}
```

上游 `TC-API-ORDERS-001` 为 `POST /api/v1/orders` 的 SCN-HAPPY，`extract.orderId` 来自 `body.data.id`。
