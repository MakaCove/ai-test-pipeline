# 08 — 端点契约驱动设计（方法论核心）

> 适用于**任意** REST / Spring MVC / 类似分层后端项目。  
> **先契约清单、后用例**：用例数量由端点复杂度（参数、校验、状态、鉴权）自然决定。

---

## 1. 为什么不用「2.5×N 条数公式」

| 问题 | 条数驱动的后果 |
|------|----------------|
| 简单 GET 详情强制 ≥4 条 | 重复 200/0 断言，无新信息 |
| 复杂 POST 创建只写 4 条 | 漏掉多个 `@NotBlank`、唯一键、状态约束 |
| 全局「安全负向≥6」 | 与不相关端点凑 OWASP 用例 |
| `variant_plan` 模板轮换 | GET 列表被标「状态迁移」 |

**正确做法**：每个端点先列出**可测契约场景**，再为每个场景写 1 条（或一组）用例。

---

## 2. 端点契约清单（Endpoint Contract Inventory）

生成用例前，对每个 `endpoints[]` 项（或每个 Controller 方法）建立契约条目。可写入 JSON 元信息 `coverage.endpointContracts`。

### 2.1 清单项结构

```json
{
  "id": "CTR-PROJECTS-POST-001",
  "endpointKey": "POST /api/v1/projects",
  "module": "projects",
  "method": "POST",
  "path": "/api/v1/projects",
  "requiresAuth": true,
  "request": {
    "contentType": "application/json",
    "bodyFields": [
      { "name": "name", "required": true, "validation": "@NotBlank" },
      { "name": "code", "required": true, "validation": "@NotBlank", "unique": true }
    ],
    "queryParams": [],
    "pathParams": []
  },
  "response": {
    "successCode": 0,
    "successFields": ["id", "name", "code"],
    "paged": false
  },
  "businessRules": ["code 项目内唯一", "软删后不可见"],
  "scenarios": [
    { "id": "SCN-HAPPY", "type": "happy", "summary": "合法 body 创建成功" },
    { "id": "SCN-V-NAME", "type": "validation", "summary": "name 为空 → 400/4002" },
    { "id": "SCN-V-CODE", "type": "validation", "summary": "code 为空 → 400/4002" },
    { "id": "SCN-A-NOAUTH", "type": "auth", "summary": "无 Bearer → 401/4010" },
    { "id": "SCN-E-DUP", "type": "business", "summary": "code 重复 → 400/4001" }
  ],
  "priority": "P0"
}
```

### 2.2 必须从源码识别的内容

| 来源 | 提取什么 |
|------|----------|
| `*Controller.java` | method、path、参数注解、`@Valid` |
| `*Dtos.java` / Request record | 字段名、类型、`@NotBlank`/`@NotNull`/`@Size` |
| `GlobalExceptionHandler` | status ↔ body.code 映射 |
| `PagedResult` / 分页 DTO | `records` vs `list` |
| Controller / Service 注释与 throw | 业务异常文案、状态前置条件 |
| `WebMvcConfig` / 拦截器 | 公开路径 vs 需鉴权 |
| `application.yml` + `auth` | 测试账号 |

**禁止**：未读 DTO 就写 `requestBody: ["name", "code"]` 而实际字段是 `projectName`。

### 2.3 场景类型（按需选用，非每端点凑满）

| type | 何时需要 | 示例 |
|------|----------|------|
| `happy` | 几乎总是 | 200 + code=0 + 关键 data |
| `validation` | 有 `@Valid` / 参数约束 | 缺必填、空串、类型错 |
| `auth` | `requiresAuth=true` | 无 token、无效 token |
| `business` | 有业务 throw / 唯一键 / 状态机 | 不存在 ID、重复 code |
| `boundary` | 分页、长度、枚举边界 | pageSize=0、超长字符串 |
| `state` | 动作端点、PATCH 状态 | cancel 已结束任务 |
| `http` | Method/Content-Type 语义 | 错误 Method（可选） |
| `security` | OWASP 可自动化项 | 越权访问他人 resourceId |
| `workflow` | 跨端点编排 | login→create→get（单独标记） |

**简单 GET 详情**：可能只需 happy + auth + business(不存在 ID) 共 3 条——**合理**。  
**复杂 POST 创建**：可能 8+ 条——**也合理**。

## 3. 从契约场景到测试用例

对每个 `scenarios[]` 项生成 **1 条用例**（或判定表多列各 1 条）：

```json
{
  "id": "TC-API-PROJECTS-003",
  "contractRef": "CTR-PROJECTS-POST-001",
  "scenarioRef": "SCN-V-CODE",
  "title": "projects - 创建项目 - code 为空校验失败",
  "designMethods": ["等价类"],
  "designRef": "EP-code-无效类-空字符串",
  "request": {
    "method": "POST",
    "path": "/api/v1/projects",
    "headers": { "Authorization": "Bearer {{token}}", "Content-Type": "application/json" },
    "body": { "name": "测试项目", "code": "" }
  },
  "assertions": [
    { "field": "status", "operator": "eq", "expected": 400 },
    { "field": "body.code", "operator": "eq", "expected": 4002 }
  ]
}
```

### 3.1 按 HTTP 方法推导场景（读代码后决定）

| 方法 | 典型场景（存在则写，不存在则跳过） |
|------|--------------------------------------|
| GET 列表 | 默认分页；每个**有意义** query 筛选 1 条；组合筛选（可选） |
| GET 详情 | happy；path id 不存在 |
| POST 创建 | happy + extract；**每个必填字段**缺 1 条；唯一键冲突 |
| PUT | happy；资源不存在 |
| PATCH | 各可 PATCH 字段；非法状态值 |
| DELETE | happy；重复删/不存在 |
| POST 动作 | 合法状态触发；非法状态 |

---

## 4. 变量链与执行顺序

1. **登录** → extract `token`（路径以 DTO 为准）。
2. **创建主数据** → extract `projectId`、`versionId` 等。
3. **依赖资源的操作** → 使用 `{{变量}}`。
4. **destructive** 用例放模块末或 `tags: ["destructive"]`。

流程用例（`workflow`）可引用多个 `contractRef`，`extract` 链须在 description 说明。

---

## 5. 验收标准

- [ ] 每个 analysis 中的 endpoint 在清单中有 `endpointContracts` 条目
- [ ] 每个 P0 端点的 `scenarios[]` 均已实现为用例（`scenarioRef` 100%）
- [ ] 断言 status + body.code 与 `GlobalExceptionHandler` 一致
- [ ] 请求体字段名与 DTO **完全一致**
- [ ] 无「仅为凑 tag/条数」而与契约无关的用例
- [ ] **不**以 `totalCases ≥ 2.5N` 作为通过/失败条件

---

## 6. 反模式

1. **模板轮换**：`for i in range(4): pool[i % 9]`。
2. **字段幻觉**：DTO 无 `owner` 却写进 body。
3. **错误码幻觉**：密码错误期望 401，实际为 400/4001。
4. **标签滥用**：只读 GET 标「状态迁移」「业务流程」却无状态变更。
5. **写死 ID**：全文件 `projectId: 1` 无 extract 链。
6. **跳过读代码**：仅依赖 project-analysis 的 summary 字段。

---

## 7. 与 project-analyzer 的关系

| project-analysis | 用途 |
|------------------|------|
| `modules[].endpoints[]` | 遍历入口，**不是**条数分配依据 |
| `auth` | 登录场景与测试账号 |
| `requestBody` / `responseBody` | 初稿，**必须**与 DTO 核对 |

analyzer 提供地图；契约清单必须 **读 Controller + DTO** 后填写。
