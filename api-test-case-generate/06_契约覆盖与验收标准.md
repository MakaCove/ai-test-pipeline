# 06 — 契约覆盖与验收标准

> 验收的是**契约场景是否测到**，不是**用例条数是否 ≥ 2.5N**。方法见 **[08_端点契约驱动设计.md](08_端点契约驱动设计.md)**。

## 1. 交付标准（优先级从高到低）

| 优先级 | 标准 | 说明 |
|--------|------|------|
| **P0** | 端点覆盖率 **100%** | analysis 中每个 endpoint 至少 1 条用例 |
| **P0** | P0 契约场景覆盖率 **100%** | 见 `contractScenarioCoveragePercent` |
| **P0** | 断言与异常处理一致 | 读 `GlobalExceptionHandler` |
| **P0** | 请求体与 DTO 字段一致 | 读 `*Dtos` / Request record |
| **P1** | 变量链可执行 | login extract → 创建 extract → 下游引用 |
| **P1** | 设计方法合理 | 每条用例有 tag，非全部「正常」 |

**不采用**：`≥ 2.5N`、`≥ 3N`、`P0 每端点 ≥ 4 条` 等**固定条数 KPI**。

## 2. 契约清单要求

生成前必须完成 **endpointContracts**（08 §2），至少包含：

- method、path、requiresAuth
- body/query/path 参数及校验注解
- 业务规则（唯一键、状态前置、软删）
- **scenarios[]**：该端点需要的测试场景列表

场景数量 **因端点而异**：

- `GET /operation-logs`（只读列表）：可能 4～6 个场景
- `POST /generation-tasks`（多字段 + 状态）：可能 10+ 个场景

## 3. 场景矩阵（参考，非强制每端点 4 格）

| 代号 | 场景 | 何时必须 |
|------|------|----------|
| H | 正常 Happy Path | 几乎所有端点 |
| V | 参数校验 | 有 `@Valid` 或参数约束 |
| A | 鉴权 | `requiresAuth=true` |
| E | 业务异常 | Controller/Service 有 throw 或唯一约束 |
| B | 边界 | 分页、长度、枚举 |
| S | 状态流转 | 动作类、PATCH 状态 |
| W | 业务流程 | 跨端点编排（单独标记） |

**不是**每个端点都勾选全部 7 类；只选**契约上存在**的维度。

## 4. 断言最低要求

成功：

```json
{ "field": "status", "operator": "eq", "expected": 200 },
{ "field": "body.code", "operator": "eq", "expected": 0 }
```

失败：同时断言 `status` 与 `body.code`（以项目异常处理为准）。

列表：确认 `PagedResult` 字段名后断言 `body.data.records` 或 `body.data.list`。

## 5. 变量链（强制）

1. 登录 extract `token`
2. 创建 extract 主键
3. 后续 `Authorization: Bearer {{token}}`
4. destructive 用例隔离或置后

## 6. 必须读取的代码（不可只靠端点清单）

| 来源 | 用途 |
|------|------|
| `*Controller.java` | 路径、方法、参数 |
| `*Dtos.java` | 字段、校验 |
| `GlobalExceptionHandler.java` | 错误码 |
| `application.yml` | 账号、前缀 |
| 拦截器/CORS 配置 | 公开路径 |

## 7. 元信息 `coverage` 必填字段

```json
{
  "endpointTotal": 95,
  "endpointsCovered": 95,
  "endpointCoveragePercent": 100,
  "contractScenarioTotal": 312,
  "contractScenariosCovered": 312,
  "contractScenarioCoveragePercent": 100,
  "uncoveredScenarios": [],
  "byModule": { "projects": 28 },
  "byDesignMethod": { "等价类": 45 },
  "designMethodsCovered": 7,
  "endpointContracts": [ { "id": "CTR-...", "scenarios": [] } ]
}
```

**不再使用** `targetMinCases`。

`totalCases` 为结果值，等于已实现的 scenario 用例数（含 workflow 额外条数）。

## 8. 与功能用例的关系

- 接口：HTTP 契约、参数、状态码、data 结构
- 功能：UI 交互、导航、Message

共享 project-analysis，**独立设计**，**不比较条数**。

## 9. 验收清单

- [ ] `endpointContracts` 来自 Controller/DTO 源码
- [ ] `endpointCoveragePercent` = 100%
- [ ] P0 `contractScenarioCoveragePercent` = 100%
- [ ] 无重复 id；鉴权端点均有 auth 场景
- [ ] 无 orphan 凑数用例（无 contractRef/scenarioRef 且非 workflow）
- [ ] `byDesignMethod` 已填
- [ ] 所有可串联场景具备“上游产出 → 下游消费”的链路表达

## 10. 自动化机检规则（建议接入脚本/CI）

推荐脚本：`scripts/validate-api-cases.mjs`

```bash
# 显式指定文件
node scripts/validate-api-cases.mjs test-artifacts/api-cases/api-cases-20260529-100000.json

# 不传参数：自动读取 test-artifacts/latest，再回退到 api-cases 目录最新文件
node scripts/validate-api-cases.mjs

# 严格模式：warning 也会导致失败
node scripts/validate-api-cases.mjs --strict

# 链路门禁：识别到可串联场景时，若无链路用例直接失败
node scripts/validate-api-cases.mjs --enforce-chain

# 可组合使用：发布前强校验
node scripts/validate-api-cases.mjs --strict --enforce-chain
```

模式说明：

- `normal`：仅 `error` 导致失败，`warning` 仅提示。
- `strict`：`error` 与 `warning` 都会导致失败。
- `enforce-chain`：识别到可串联场景时，必须存在链路用例表达。

### 10.1 结构与 schema

- [ ] 顶层为数组，且长度 `>= 2`
- [ ] 首元素 `schema === "ai-test-pipeline/api-case/v1"`
- [ ] 首元素存在 `coverage` 且包含 `endpointTotal/endpointsCovered/contractScenarioTotal/contractScenariosCovered/endpointContracts`

### 10.2 覆盖率与一致性

- [ ] `endpointCoveragePercent === Math.round(endpointsCovered / endpointTotal * 100)`（`endpointTotal > 0`）
- [ ] `contractScenarioCoveragePercent === Math.round(contractScenariosCovered / contractScenarioTotal * 100)`（`contractScenarioTotal > 0`）
- [ ] `uncoveredScenarios` 为空数组（若字段存在）

### 10.3 追溯完整性

- [ ] 单端点用例必须有 `contractRef` 与 `scenarioRef`
- [ ] 流程用例可使用 `contractRefs`，但必须有 `scenarioRef`
- [ ] 每个 `contractRef/contractRefs[*]` 必须存在于 `coverage.endpointContracts[].id`
- [ ] `orphanCases === 0`

### 10.4 链路完整性（通用）

- [ ] 可串联场景应至少有一条链路用例（推荐 `TC-API-WF-*`）
- [ ] 若存在 `dependsOnCases`，依赖 id 必须可解析
- [ ] 若存在 `consumes`，应能在当前用例 `produces` 或上游依赖用例 `produces` 中找到来源
- [ ] `flowChains` 存在时，覆盖率计算应自洽

### 10.5 质量与反硬编码

- [ ] 每条用例 `request` 非空且 `assertions.length >= 2`
- [ ] `id` 全局唯一，推荐匹配 `^TC-API-[A-Z0-9-]+$`
- [ ] 登录类请求优先使用 `{{username}}/{{password}}` 占位
- [ ] 不允许默认口令硬编码（如 `admin` / `123admin`）
- [ ] 创建型请求建议使用 `{{timestamp}}` 或等效唯一后缀

## 11. 反模式

- 未读 DTO 生成 body。
- 每端点机械 4 条 happy/validation/auth/boundary。
- 为达标全局 tag 下限添加无关用例。
- Skill 或脚本写死某一项目的模块名与 N 值。
