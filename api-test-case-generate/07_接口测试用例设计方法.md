# 07 — 接口测试用例设计方法

> 生成本技能接口用例时，须按 **ISTQB**、**ISO/IEC/IEEE 29119**、**REST/HTTP 语义** 与 **OWASP API Security** 等业界共识组织用例，落实到 `request` 与 `assertions`（`status` + `body.code` + 关键 `data`）。  
> 每条用例在 `tags` / `designMethods` 中标注**主设计方法**（1～2 个）；`designRef` 写明标准条款或规则编号。

## 0. 标准依据（生成时应对齐）

| 标准/指南 | 与本技能的关系 |
|-----------|----------------|
| **ISTQB CTFL** §4.2 | 黑盒技术：等价类、边界值、判定表、状态迁移 |
| **ISTQB CTFL** §4.4 | 经验技术：错误推测 |
| **ISO/IEC/IEEE 29119-4** | 测试设计技术选用、组合测试（Pairwise） |
| **RFC 9110**（HTTP 语义） | 方法幂等性、状态码、安全方法 |
| **Richardson REST 成熟度** | 资源 URI、动词用 HTTP Method 表达 |
| **OpenAPI 3.x**（若有） | 契约：路径、参数、响应 schema |
| **OWASP API Security Top 10** | 鉴权、对象级授权、输入验证等负向用例 |

**说明**：国内教材常列「八大方法」（含因果图、正交试验）。行业中 **因果图**多用于**设计阶段**导出判定表，执行层统一标 `判定表`；**正交试验**在工程上多落实为 **Pairwise/组合测试**（29119），本技能用 tag **`组合测试`**。

## 1. 方法分类体系（接口专用）

### 1.1 基于规格的黑盒技术（ISTQB — 必掌握）

| tag | 英文 | 适用 |
|-----|------|------|
| `等价类` | Equivalence Partitioning | body/query/path/header 有效类与无效类 |
| `边界值` | Boundary Value Analysis | 长度、数值、分页、枚举边界 |
| `判定表` | Decision Table Testing | 多条件→多响应（登录、多 ID 提交、鉴权×资源） |
| `状态迁移` | State Transition Testing | 资源生命周期、动作端点、PATCH 状态 |

### 1.2 组合测试（ISO 29119 — 多参数端点）

| tag | 英文 | 适用 |
|-----|------|------|
| `组合测试` | Pairwise / Combinatorial | 列表多 query、创建多外键字段；2-way 为主 |

### 1.3 API 流程与契约（行业实践 — 接口层必做）

| tag | 英文 | 适用 |
|-----|------|------|
| `业务流程` | API Workflow / Orchestration | 多调用链：login→create→action→assert |
| `HTTP语义` | HTTP Semantics Matrix | Method×路径×鉴权×Content-Type×期望 status |
| `契约校验` | Contract / Schema Validation | 与 OpenAPI 或 Controller 响应结构一致（有文档时） |

### 1.4 经验与安全（ISTQB + OWASP — 负向补充）

| tag | 英文 | 适用 |
|-----|------|------|
| `错误推测` | Error Guessing | 缺字段、畸形 JSON、重复提交、错误 Method |
| `安全负向` | Security Negative | 未授权、越权 ID、Token 篡改、注入类 payload |

**模块级要求**：设计方法 tag 应覆盖该模块**已识别契约场景**的类型；**等价类** + **业务流程**（若存在跨端点链）优先选用。  
**不以**全文件某 tag 固定条数为验收条件（见 06、08）。

**与 06 场景矩阵**：06 的 H/V/A/B/E/S 是**契约覆盖维度**；本章是**设计方法**。可并存（例：参数校验 V + tag `等价类`）。

### 1.5 旧 tag 兼容映射

| 旧 tag | 新 tag | 说明 |
|--------|--------|------|
| `场景` | `业务流程` | 优先用 `业务流程` |
| `正交` | `组合测试` | Pairwise 为行业默认术语 |
| `因果图` | `判定表` | 设计时用因果图，执行用例标 `判定表`，`designRef` 注明 CE→DT |

## 2. 各方法落地要点

### 2.1 等价类划分（Equivalence Partitioning）

将每个输入参数划分为**有效类 / 无效类**，每类至少 1 条代表用例。

| 位置 | 有效类 | 无效类 |
|------|--------|--------|
| `body.username` | 已注册 `autotest` | 空、未注册、纯空格 |
| `body.code` | 唯一合法编码 | 空、重复、非法字符 |
| `query.status` | 枚举内值 | 非法字符串 |
| `path.id` | `{{projectId}}` | 不存在、非数字 |

- 断言须含 **status + body.code**（读 `GlobalExceptionHandler`）。
- `designRef` 示例：`EP-PROJECT-code-无效类-空字符串`。

### 2.2 边界值分析（Boundary Value Analysis）

覆盖 **min、min+1、max、max-1、刚越界**（ISTQB 四点法可化简为 min/max/越界）。

| 约束 | 用例值 |
|------|--------|
| 长度 3～32 | 2, 3, 32, 33 |
| `pageNo` / `pageSize` | 1, 0, 超大 pageSize |
| 分页最后一页 | 合法边界内无数据 vs 有数据 |

### 2.3 判定表测试（Decision Table Testing）

**登录示例**（每列 ≥1 条用例）：

| 条件 | R1 | R2 | R3 | R4 |
|------|----|----|----|-----|
| 用户存在 | Y | Y | N | N |
| 密码正确 | Y | N | Y | N |
| 期望 | 200,code=0 | 400,4001 | 400,4001 | 400,4001 |

**必做判定表**：`auth/login`；`POST generation-tasks`（多引用 ID）；鉴权×资源存在性。

### 2.4 状态迁移测试（State Transition Testing）

覆盖：**合法迁移**、**非法迁移**、**迁移后 GET 校验**。

| 对象 | 迁移 | API |
|------|------|-----|
| 版本 | DRAFT→PUBLISHED | POST publish |
| 生成任务 | QUEUED→RUNNING→终态 | start/cancel/retry |
| 用例评审 | PENDING→APPROVED | PATCH status |

断言：`body.data.status`（或实际字段）与迁移目标一致。

### 2.5 组合测试（Pairwise / Combinatorial）

对 **≥3 个独立因子** 的列表 query 或创建 body，采用 **2-way Pairwise**（因子各 2～3 水平），每模块 **≥4 条**。

```
因子: projectId(A/B) × versionId(v1/v2) × status(PENDING/DONE) × keyword(空/有)
→ 选取 Pairwise 最小集，非全因子ial 爆炸
```

`designRef`：`PAIRWISE-行3` 或工具表编号。

### 2.6 业务流程 / API 编排（Workflow）

对应 ISTQB **用例测试**在 API 层的实现：主成功路径 + 关键备选流。

| 编号 | 流程 | 链 |
|------|------|-----|
| WF-01 | 交付物准备 | login→project→version→asset |
| WF-02 | 生成闭环 | asset→POST task→GET→cancel/retry |
| WF-03 | 用例评审 | POST case→PATCH→GET filter |
| WF-04 | 接口用例库 | POST api-case→PUT→GET |
| WF-05 | 导出 | POST export→GET status |
| WF-06 | UI-NL | case→task→report |

全文件 **`业务流程`** 覆盖已识别的跨端点主路径；extract 变量连贯；`tags` 含 `业务流程`。

### 2.7 HTTP 语义矩阵（HTTP Semantics）

按 **RFC 9110** 验证 Method、鉴权、Content-Type 与响应码组合（每 P0 模块 ≥2 条）：

| 维度 | 示例 |
|------|------|
| 鉴权 | 无 Bearer → 401 + 4010 |
| Method | 对只读资源 POST → 405/400 |
| Content-Type | 非 `application/json` → 415/400 |
| 幂等 | 重复 DELETE 第二次行为（404 或 200） |

`tags`：`HTTP语义`。

### 2.8 契约校验（Contract Validation）

当存在 OpenAPI 或稳定 DTO 时：

- 成功响应：关键字段 **type/exists**（`body.data.*`）。
- 列表：`records`/`list` 与分页字段名与 `PagedResult` 一致。
- 错误响应：`body.code` 与文档枚举一致。

`tags`：`契约校验`（无 OpenAPI 时仍可按 Controller 注解做弱契约）。

### 2.9 错误推测（Error Guessing）

ISTQB 经验法：按端点契约推测易错点（缺 Authorization、畸形 JSON、重复唯一键等）。

### 2.10 安全负向（OWASP API Security）

从 **API Top 10** 选取可自动化项，在**相关端点**的契约场景中出现即可：

| OWASP 类 | 用例方向 |
|----------|----------|
| API1 对象级授权 | 用他人 `projectId` 访问 |
| API2 认证失效 | 无效/过期 Token |
| API8 输入验证 | 超长、特殊字符、类型混淆 |
| API3 属性级（若适用） | 修改只读字段 |

`tags`：`安全负向`；与纯业务 `错误推测` 区分。

## 5. 验收清单（与 06、08 合并）

- [ ] 每个 P0 端点的 `scenarios[]` 均有对应用例（`scenarioRef`）
- [ ] 有 `@Valid` 的 body：必填字段校验场景齐全
- [ ] 需鉴权端点：auth 场景齐全

- [ ] 动作/状态端点：状态迁移场景有断言
- [ ] 多 query 列表：必要时组合测试，非机械全排列
- [ ] `coverage.byDesignMethod` 已填，非 100% 单一 tag
- [ ] 无仅为凑 tag/条数而与契约无关的用例

## 6. 反模式

- 仅标 `正常`、`冒烟`，无设计方法 tag。
- 把单接口 GET 标为 `业务流程`且无 extract 链说明。
- 判定表只覆盖 R1（全成功）。
- 用 `因果图`/`正交` 作执行 tag 而不迁移到 `判定表`/`组合测试`。
- 安全与业务失败混为一条，无法区分 OWASP 类。
- 为达到 tag/条数 KPI 而添加与契约清单无关的用例。
