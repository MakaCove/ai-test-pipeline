# UI 主流程识别与设计

> **只生成符合业务的主流程 UI 用例**：步骤来自真实用户操作路径，控件文案来自页面源码。
> 不为每个路由、每个表单校验、每个筛选条件单独写用例。

---

## 1. 交付目标

| 维度 | 目标 |
|------|------|
| 用例数量 | **不设上限**；项目识别出多少条主流程，就生成多少条对应用例 |
| 覆盖范围 | **所有从源码识别出的业务主路径**，不是全站功能点穷举 |
| 步骤来源 | 布局菜单 + 页面源码中的真实按钮/表单文案 |
| 链路表达 | 跨页/跨模块流程用 `dependsOnCases` + 同一 `trace.flowRefs` |
| 用例 ID | 统一 `TC-FUNC-{MODULE}-{序号}`（登录为 `TC-FUNC-AUTH-*`） |

**验收口径**：识别出的每条主流程都有 1 条可执行用例，且步骤能在源码中找到依据。

---

## 2. 主流程是什么

主流程 = 用户完成一项**核心业务目标**所需的最短、最常见操作序列。

| 类型 | 示例 | 识别信号（源码） |
|------|------|------------------|
| 会话入口 | 登录进入工作台 | `/login` 表单 + 登录 API + 跳转首页 |
| 资源生命周期 | 创建 → 列表可见 → 编辑/提交 | POST 创建 + 列表页 refresh + 行内「编辑/提交」按钮 |
| 审批/状态流转 | 草稿 → 提交 → 待审 | 状态 tag + 「提交审核」按钮 + PUT/PATCH API |
| 跨模块串联 | 先建 A，再在 B 中引用 A | B 页下拉/选择器依赖 A 的 API 或 store |
| 关键交易 | 下单、支付、发布 | 多步 wizard 或确认弹窗 + 最终 POST |

**不是主流程**（默认不写单独用例）：

- 单字段校验失败、边界值、空列表展示
- 分页、排序、高级筛选的各种组合
- 纯配置页、日志页、只读统计页
- 注册/找回密码（除非产品明确为核心入口）
- 路由守卫专项、深链专项（除非用户明确要求）

## 3. 识别步骤（从代码到主流程清单）

### 3.1 读输入

1. `project-analysis`：`modules`、`routes`、`auth`、`chainHints`、**`pageEntryHints`**、**`mainFlowCandidates`**
2. 布局组件：侧栏/顶栏 → `routeMenuMap`（见 [菜单导航与步骤.md](菜单导航与步骤.md)）
3. **相关页面源码**：凡涉及主流程的 View/Page 都要读，深度与流程复杂度匹配

### 3.2 优先确认 mainFlowCandidates 与 pageEntryHints

- `mainFlowCandidates`：UI 侧主流程候选，逐条确认/排除
- `pageEntryHints[].actions`：每个页面的可点击操作，判断是否涉及副作用（创建/修改/删除/提交/审批/导出）
- 有副作用的操作 → 对应的流程是否在 `mainFlowInventory` 中？未覆盖则补充

### 3.3 找「业务动词」

在页面源码中搜索用户可触发的**业务动作**（不是每个 input）：

- 提交类：`提交`、`保存`、`创建`、`发布`、`审核`、`确认`
- 流转类：`下一步`、`完成`、`通过`、`驳回`
- 关联类：`选择`、`关联`、`导入`、`分配`

每个动词对应：触发的 API（`api/`、`services/`）、成功后 UI 反馈（跳转、toast、列表刷新）。

### 3.4 串成主流程

按业务语义合并为 **1 条端到端路径**，写入 `coverage.mainFlowInventory[]`：

```json
{
  "id": "FLOW-PROJECTS-001",
  "name": "项目创建到提交审核",
  "module": "projects",
  "priority": "P0",
  "userGoal": "业务用户创建项目并提交审核",
  "menuPath": ["项目管理"],
  "routes": ["/projects", "/projects/create"],
  "stepsSummary": "登录 → 菜单进入项目 → 新建 → 填表提交 → 列表出现记录 → 提交审核",
  "evidence": [
    "ProjectsView.vue: 新建项目按钮",
    "ProjectForm.vue: POST /api/v1/projects",
    "ProjectList.vue: 提交审核操作列"
  ],
  "suggestedCaseIds": ["TC-FUNC-PROJECTS-001"],
  "chainVars": ["projectName"],
  "confidence": "high"
}
```

### 3.5 数量原则（不设上限）

- **有多少真实主流程，就列多少条**
- 每条主流程必须在源码中有明确依据（`evidence`），且能一句话说清 `userGoal`
- 若某条看似主流程，实质是「单字段校验 / 分页 / 筛选 / 打开页面」，则**不要**入清单

## 4. 用例编写规则

### 4.1 一条主流程 = 一条或多条用例

- 简单主流程：1 条 `TC-FUNC-{模块}-{序号}` 覆盖全程
- 复杂/跨模块主流程：可拆成多条用例，用 `trace.dependsOn` 串联；均指向同一 `trace.flowRefs`
- 步骤：**会话 → 菜单导航 → 连续功能操作**
- 断言：验证**流程终点**的 UI 状态（URL、关键文案、元素可见），≥2 条

### 4.2 登录/session 基础

- 写 **1 条** `TC-FUNC-AUTH-001`（登录主成功路径），`trace.produces: ["sessionUser"]`
- 其余流程：`trace.dependsOn: ["TC-FUNC-AUTH-001"]` + `ensure_session` 开头

不要在每条用例里重复完整登录步骤。

### 4.3 trace 分组（链路字段）

```json
{
  "id": "TC-FUNC-ORDERS-001",
  "title": "创建订单并在列表可见",
  "module": "orders",
  "priority": "P0",
  "trace": {
    "flowRefs": ["FLOW-ORDERS-001"],
    "dependsOn": ["TC-FUNC-AUTH-001"],
    "produces": ["orderTitle"],
    "consumes": ["sessionUser"]
  },
  "steps": ["..."],
  "assertions": ["..."]
}
```

### 4.4 步骤必须可执行

| 要求 | 说明 |
|------|------|
| 菜单进入 | 业务页用 `click_menu`，不用 `navigate` 直链 |
| 文案真实 | `target` 来自源码中的 label/button/placeholder |
| 数据唯一 | 创建类用 `AUTO-{{timestamp}}`，避免污染环境 |
| 等待 | 导航或提交后 `wait` 500～1500ms |

### 4.5 跨模块数据

上游流程 `trace.produces` / `saveAs` 变量，下游 `trace.consumes` / `useVar`：

```
FLOW-A 创建资源 → trace.produces: ["resourceName"]
FLOW-B 引用资源 → trace.consumes: ["resourceName"]
```

## 5. 菜单遍历法（强制 · 防止遗漏）

识别完主流程后，必须用菜单遍历法兜底：

```
对 routeMenuMap 中每个一级菜单：
  □ 打开该菜单对应页面
  □ 扫描页面中所有可点击按钮/操作
  □ 判断：是否涉及副作用操作？（创建/修改/删除/提交/审批/导出）
  □ 如果是：该操作对应的主流程是否在 mainFlowInventory 中？

未覆盖的操作必须写明原因（"该操作是只读/配置类"），否则视为遗漏。
```

## 7. 验收清单

- [ ] `coverage.mainFlowInventory` 已填写，每条有 `evidence`
- [ ] 每条主流程有对应用例（`suggestedCaseIds` 中每个 id 均存在）
- [ ] 用例步骤可在源码中找到控件依据
- [ ] 业务页经 `click_menu` 进入，`routeMenuMap` 已填写
- [ ] 登录/session 未重复编写；`trace.dependsOn` 链可解析
- [ ] 未生成大量「打开页面 / 校验失败 / 分页」类碎片用例
- [ ] 菜单遍历法已完成，未覆盖操作有说明

## 8. 反模式

- 按路由数 × 固定模板批量生成
- 未读页面就写「点击确定」
- 把 10 个校验分支拆成 10 条主流程用例
- 用 `navigate /业务路由` 代替菜单操作
- 追求 `featureCoveragePercent = 100%` 而补无关用例
- 仅凭"灵感"归纳主流程，不做菜单遍历
