# 08 — 功能清单驱动设计（方法论核心）

> 本技能适用于**任意** Web 前端项目（Vue / React / 等），不绑定某一业务域。  
> **先清单、后用例**：用例数量是功能复杂度的自然结果，不是预设 KPI。

---

## 1. 为什么不用「条数下限」

| 问题 | 条数驱动的后果 |
|------|----------------|
| 页面简单却强制 ≥4 条 | 重复「打开页面」、无差异断言 |
| 页面复杂却只写 4 条 | 批量操作、状态机、多 Tab 漏测 |
| 与接口用例比数量 |  UI 与 API 验证维度不同，不应强行对齐 |

**正确做法**：先回答「这个页面/模块有哪些**可测功能点**」，再回答「每个功能点需要哪些**测试场景**」。

---

## 2. 功能清单（Feature Inventory）

生成用例前，**每个路由**（或每个 `*View.vue` / `*Page.tsx`）输出一张清单。可写在对话中，或写入 JSON 元信息 `coverage.featureInventory`。

### 2.1 清单项结构

```json
{
  "id": "FEAT-PROJECTS-003",
  "route": "/projects",
  "module": "projects",
  "type": "dialog|form|table-action|filter|navigation|auth|async|readonly",
  "name": "新增项目",
  "trigger": "点击「新增项目」",
  "elements": ["项目名", "项目编码", "确认新增", "取消"],
  "validations": ["必填项为空时前端提示"],
  "sideEffects": ["列表刷新", "ElMessage 成功"],
  "relatedApis": ["POST /api/v1/projects"],
  "priority": "P0"
}
```

### 2.2 必须从源码识别的类型

| type | 识别来源（示例） | 典型测试场景 |
|------|------------------|--------------|
| `navigation` | 侧栏、router-link、菜单 | 跳转 URL、需登录 |
| `form` | el-form、Form、input | 有效提交、校验失败 |
| `dialog` | el-dialog、Modal | 打开/关闭、确认/取消 |
| `table-action` | 操作列 link/button | 编辑、删除、详情 |
| `filter` | 搜索框、select + 查询 | 单条件、组合、重置 |
| `batch` | 多选 + 批量按钮 | 未选禁用、批量成功 |
| `pagination` | el-pagination | 翻页、每页条数 |
| `state-display` | 状态 tag、进度 | 与后端状态一致 |
| `async` | 提交任务、轮询 | 提交、取消、重试 |
| `auth` | 登录、登出、重定向 | 见 07 判定表 |
| `readonly` | 纯展示、日志 | 加载、筛选 |

**规则**：页面上**真实存在**且**用户可感知**的交互，都应成为清单项；纯静态文案可合并为 1 条「页面可访问/关键信息可见」。

### 2.3 扫描步骤（通用）

1. `router` 配置 → 路由 path、component、meta（`requiresAuth` 等）。
2. 打开页面组件 → 模板中的按钮、表单、对话框、表格列。
3. `script` / hooks → 事件处理函数名（`onCreate`、`handleDelete`）辅助理解业务。
4. `api` 层 → 该页调用的接口，写入 `relatedApis`（description 可追溯）。
5. 全局布局 → 侧栏、顶栏、登出入口（若影响测试前置）。

**禁止**：未打开文件就写「查询、新增、编辑、删除」四件套。

## 3. 从功能点到测试场景

对每个清单项 `FEAT-xxx`，按 **07 设计方法** 推导场景（按需选用，非每项都凑满 8 种 tag）：

| 功能特征 | 推荐设计方法 | 示例 |
|----------|--------------|------|
| 输入框 + 提交 | 等价类、边界值 | 合法名称 / 空 / 超长 |
| 多条件筛选 | 组合测试、判定表 | 项目×状态×关键词 |
| 登录/权限 | 判定表、错误推测 | 用户×密码×是否跳转 |
| 任务/订单状态 | 状态迁移 | 草稿→发布→不可编辑 |
| 主业务流程 | 用例场景 | 登录→创建→使用→清理 |
| 易错操作 | 错误推测 | 未选行点批量、双击提交 |
| 发布前冒烟 | 检查清单 | 关键按钮可见可点 |

**一条用例只验证一个明确目标**；复杂流程拆成「用例场景」串联，或 preconditions 注明前置数据。

## 4. 用例与功能点的追溯

每条用例推荐字段：

```json
{
  "id": "TC-FUNC-PROJECTS-003",
  "featureRef": "FEAT-PROJECTS-003",
  "title": "项目管理 - 新增项目 - 合法信息提交成功",
  "designMethods": ["等价类"],
  "designRef": "EP-项目名-有效类"
}
```

元信息 `coverage` 中统计：

- `featureTotal`：清单项总数（P0/P1 分开计可选）
- `featuresCovered`：至少 1 条用例引用的功能点数
- `featureCoveragePercent`：P0 功能点覆盖率，目标 **100%**
- `orphanCases`：无 `featureRef` 的用例数，应为 **0**（流程用例可引用多个 featureRef 数组）

---

## 5. 跨页面业务流程（覆盖 + 链路）

当 `project-analysis` 或业务文档存在**端到端故事**时，额外编写「用例场景」：

- 只编排**真实存在**的页面与操作，步骤 ≥6 且跨 ≥2 路由；
- `featureRefs` 列出涉及的功能点；
- 对可串联场景增加 `dependsOnCases` / `produces` / `consumes`（详见 `09_功能数据链路驱动设计.md`）；
- 不编造系统中不存在的页面。

示例结构（业务无关）：

```
UC-01 主成功路径：登录 → 模块 A 创建主数据 → 模块 B 引用 → 模块 C 查看结果
UC-02 异常流：未登录访问受保护页 → 重定向登录
UC-03 清理：创建后 teardown 删除（或唯一编码可重复执行）
```

---

## 6. 验收标准（功能驱动）

生成完成前自检：

- [ ] 每个路由至少扫描过对应页面源码
- [ ] `featureInventory` 已产出且 P0 项无遗漏
- [ ] 每个 P0 功能点有 ≥1 条用例，`featureCoveragePercent` = 100%
- [ ] 可串联场景具备“先产出后消费”的链路表达
- [ ] 无重复 `id`；无空 `steps` / `assertions`
- [ ] 所有 `steps[].target` 与页面文案一致（或注明 selector 策略）
- [ ] **未**出现「同一模板复制 N 次仅改标题」的凑数用例

**不要求**达到固定总条数。若功能简单，30 条高质量用例优于 150 条重复用例。

---

## 7. 反模式（出现即退回重做）

1. **模板循环**：所有列表页共用相同的 4 步「登录→进入→点查询→断言表格」。
2. **控件幻觉**：页面是「进入工作台」却写「登录按钮」。
3. **功能遗漏**：页面有「批量删除」「评审弹窗」但清单中未列出。
4. **为对齐接口数而注水**：接口 200 条 ≠ 功能也要 200 条。
5. **无 featureRef**：大批量用例无法说明测了哪个功能。

---

## 8. 与 project-analyzer 的关系

| project-analysis 字段 | 用途 |
|----------------------|------|
| `modules[].routes[]` | 路由遍历入口，**不是**用例条数分配依据 |
| `modules[].routes[].summary` | 清单初稿提示，须源码核实 |
| `modules[].endpoints[]` | 写 `relatedApis`、description 追溯 |
| `auth` | 登录/账号类功能点 |

analyzer 提供**地图**；功能清单与用例必须**读代码**后填写。
