# 06 — 功能覆盖与验收标准

> 验收的是**功能点是否测到**，不是**用例条数是否够多**。方法见 **[08_功能清单驱动设计.md](08_功能清单驱动设计.md)**。

## 1. 交付标准（优先级从高到低）

| 优先级 | 标准 | 说明 |
|--------|------|------|
| **P0** | P0 功能点覆盖率 **100%** | 见 `coverage.featureCoveragePercent` |
| **P0** | 路由覆盖率 **100%** | 每个 `routes[]` 至少 1 条用例且来自真实功能 |
| **P0** | 源码一致性 | 控件文案与 `*View.vue` / 页面组件一致 |
| **P0** | 导航路径合规 | `navigationModel: menu-driven`；业务用例经 `click_menu` 进入页面 |
| **P1** | 设计方法合理 | 每条用例有主设计方法 tag，非全部「冒烟」 |
| **P1** | 主成功路径 + 关键异常 | 登录、创建、权限、校验等按 07 推导 |
| **P2** | P1 功能点覆盖 | 尽量完整，可标注后续迭代 |

**不采用**：固定公式 `totalCases ≥ 3R`、`≥ 8R`、与接口用例比例等**条数 KPI**。

## 2. 功能清单要求

生成前必须完成 **featureInventory**（08 §2），至少包含：

- 每个路由上的：导航、表单、弹窗、表格操作、筛选、分页（若存在）、批量（若存在）
- 全局：登录/登出、未登录重定向（若存在）
- 跨页：识别到的端到端业务流程

清单项数量 **因项目而异**；简单 CRUD 可能 5 项/页，复杂任务中心可能 15+ 项/页。

## 3. 用例质量门槛

| 项 | 要求 |
|----|------|
| `steps` | 常规 ≥3 步；端到端流程 ≥6 步 |
| `assertions` | ≥2 条，且与验证目标相关 |
| `featureRef` | 推荐必填；流程用例可用 `featureRefs[]` |
| `description` | 用户视角 + 测什么 + 预期 UI 反馈 |
| `teardown` | 有持久化副作用时清理或唯一数据策略 |
| `wait` | 异步加载后 500～1500ms |

## 4. 路由 vs 功能点

- **路由覆盖**：没有路由被完全忽略。
- **功能覆盖**：路由内每个 P0 交互都有对应用例。

可能出现：1 个路由 25 条用例（功能多），另 1 个路由 2 条（只读且交互少）——**均合理**。

## 5. 元信息 `coverage` 必填字段

```json
{
  "routeTotal": 20,
  "routesCovered": 20,
  "routeCoveragePercent": 100,
  "featureTotal": 86,
  "featuresCovered": 86,
  "featureCoveragePercent": 100,
  "byModule": { "projects": 14 },
  "byDesignMethod": { "等价类": 22, "用例场景": 5 },
  "designMethodsCovered": 6,
  "featureInventory": [ { "id": "FEAT-...", "name": "...", "route": "..." } ]
}
```

可选：`uncoveredFeatures: []`（应为空数组才通过）。

**不再使用** `targetMinCases` 作为硬性字段。

## 6. 必须扫描的前端源码

对每个路由（通用路径，按技术栈替换）：

| 栈 | 路由 | 页面 |
|----|------|------|
| Vue | `src/router/**` | `src/views/**/*.vue` |
| React | `src/routes/**` 或 `App.tsx` | `src/pages/**/*` |
| 通用 | layout / 侧栏组件 | 按钮、表单、表格 |

并读取 `src/api/**` 或等价 HTTP 客户端，标注 `relatedApis`。

**布局（P0）**：读取侧栏/顶栏组件，产出 `routeMenuMap`（见 [10_用户操作路径驱动设计.md](10_用户操作路径驱动设计.md)）。

## 7. 与接口用例的关系

- **功能用例**：UI 行为、导航、表单、消息、权限体验。
- **接口用例**：HTTP 契约、参数、状态码。

二者**互补**，数量无需对齐。功能侧以 **featureInventory** 为准，接口侧以 **endpoints** 为准。

## 8. 验收清单

- [ ] `featureInventory` 已生成且来自源码
- [ ] P0 `featureCoveragePercent` = 100%
- [ ] `routeCoveragePercent` = 100%
- [ ] 无 orphan 凑数用例（无 featureRef 且非标注的跨页流程）
- [ ] `byDesignMethod` 已填，非单一 tag
- [ ] 无空 steps/assertions、无重复 id
- [ ] 所有可串联场景具备“上游产出 → 下游消费”的链路表达
- [ ] `navigationModel === "menu-driven"` 且 `routeMenuMap` 已填写
- [ ] 除守卫/深链专项外，业务用例无 `navigate` 进入菜单可达页面
- [ ] 所有 `click_menu` 文案可在 `routeMenuMap` 或 `featureInventory` 中找到
- [ ] **智能编排已完成**（11 §12）：`executionOrder` 连续、登录置前、破坏性认证置后

## 9. 自动化机检规则（建议接入脚本/CI）

以下规则可直接用于脚本判定 PASS/FAIL：

推荐脚本：`scripts/validate-functional-cases.mjs`

```bash
# 显式指定文件
node scripts/validate-functional-cases.mjs test-artifacts/functional-cases/functional-cases-20260529-092700.json

# 不传参数：自动读取 test-artifacts/latest，再回退到 functional-cases 目录最新文件
node scripts/validate-functional-cases.mjs

# 严格模式：warning 也会导致失败（适合发布前/主分支门禁）
node scripts/validate-functional-cases.mjs --strict

# 链路门禁：识别到可串联场景时，若无链路用例直接失败
node scripts/validate-functional-cases.mjs --enforce-chain

# 可组合使用：发布前强校验
node scripts/validate-functional-cases.mjs --strict --enforce-chain
```

模式说明：

- `normal`：仅 `error` 导致失败，`warning` 仅提示。
- `strict`：`error` 与 `warning` 都会导致失败。
- `enforce-chain`：当识别到可串联场景（声明或推断）时，必须存在链路用例表达。

### 9.1 结构与 schema

- [ ] 顶层为数组，且长度 `>= 2`
- [ ] 首元素 `schema === "ai-test-pipeline/functional-case/v1"`
- [ ] 首元素存在 `coverage` 且包含 `routeTotal/routesCovered/featureTotal/featuresCovered/featureCoveragePercent/featureInventory`

### 9.2 覆盖率与一致性

- [ ] `routeCoveragePercent === Math.round(routesCovered / routeTotal * 100)`（`routeTotal > 0`）
- [ ] `featureCoveragePercent === Math.round(featuresCovered / featureTotal * 100)`（`featureTotal > 0`）
- [ ] P0 功能点覆盖率必须 100（可通过 `featureInventory.priority==="P0"` 与引用关系复算）
- [ ] `uncoveredFeatures` 为空数组（若字段存在）

### 9.3 追溯完整性

- [ ] 每条非流程用例必须有 `featureRef`
- [ ] 流程用例必须有非空 `featureRefs` 数组
- [ ] 每个 `featureRef` / `featureRefs[*]` 必须存在于 `coverage.featureInventory[].id`
- [ ] `orphanCases === 0`

### 9.4 链路完整性（通用）

- [ ] 可串联场景应至少有一条链路用例（推荐 `TC-FUNC-WF-*`）
- [ ] 若存在 `dependsOnCases`，则依赖 id 必须在当前文件可解析
- [ ] 若存在 `consumes`，则应有同链路上游用例 `produces` 对应变量
- [ ] 若存在 `steps[].useVar`，推荐在当前用例前序步骤或上游用例中出现 `saveAs`/`produces`

### 9.5 用例质量下限

- [ ] 每条用例 `steps.length >= 1`，且 P0 用例建议 `>= 3`
- [ ] 每条用例 `assertions.length >= 2`
- [ ] `id` 全局唯一，推荐匹配 `^TC-FUNC-[A-Z0-9-]+$`
- [ ] `module` 非空，且与 `featureInventory` 中对应功能点模块一致

### 9.6 反硬编码检查

- [ ] 不允许默认账号口令硬编码（如 `admin` / `123admin`）
- [ ] 登录类步骤优先使用变量占位：`{{username}}`、`{{password}}`
- [ ] 涉及创建数据的步骤建议使用唯一后缀（如 `{{timestamp}}`）避免污染环境

> 建议：将机检失败信息按「结构错误 / 覆盖不足 / 追溯缺失 / 质量不达标」分类输出，便于快速修复。

### 9.7 导航路径（menu-driven）

- [ ] 首元素 `navigationModel === "menu-driven"`（若字段存在则必须为该值）
- [ ] `coverage.routeMenuMap` 为非空数组，且每个需登录业务路由有 `menuLabel`
- [ ] 业务模块用例（`module !== "auth"` 或 feature 非守卫类）不得使用 `navigate` 进入 `routeMenuMap` 中已登记路由
- [ ] 注册类用例须含 `switch_auth_tab`；登录负向用例须含 `reset_session`
- [ ] `click_menu` 的 target 须出现在 `routeMenuMap[].menuLabel` 中

## 10. 反模式

- 未读页面就按 L/F/C/E 模板生成。
- 用 `while count < N` 循环模板（脚本反模式同样禁止）。
- 把「打开页面」算 4 条不同用例。
- 用 `navigate /{route}` 代替侧栏菜单进入业务功能（全模块，不仅 auth）。
- 在 skill 或脚本里写死某一项目的模块名/条数。
