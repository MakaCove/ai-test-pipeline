# 智能编排（功能/UI 用例 · 通用）

> **适用任意前后端分离项目**，不绑定具体路由、菜单文案或生成脚本。  
> 目标：UI 执行时变量可复用、会话不被中途破坏、上下游功能顺序可执行。  
> 原则：**登录引导 → 业务生产 → 查询/编辑 → 删除 → 破坏性认证置后。**

与相邻文档的关系：

- **[菜单导航与步骤.md](菜单导航与步骤.md)**：步骤**怎么点**（菜单 → 模块 → 操作）
- **[主流程识别与设计.md](主流程识别与设计.md) §4.4**：功能间**谁生产、谁消费**
- **本文件**：用例**以什么顺序执行**、变量如何跨用例传递

**智能编排不替代菜单导航**；只决定执行顺序与会话/数据链。

---

## 1. 何时必须编排

功能用例全部编写完成、写入 JSON 之前，Agent 必须执行本章流程。

触发信号：

| 信号 | 示例 |
|------|------|
| 步骤含 `saveAs` / `useVar` | 创建订单后保存 `orderName` |
| 步骤 value/target 含 `{{var}}` | 筛选框填入 `{{projectName}}` |
| 已声明 `dependsOnCases` / `produces` / `consumes` | 编辑依赖创建 |
| 功能语义破坏会话 | 退出登录、修改密码、切换账号 |
| `featureInventory` 存在生命周期链 | 创建→编辑→删除 |

---

## 2. 输入（项目无关）

| 输入 | 用途 |
|------|------|
| `coverage.featureInventory[]` | 功能类型、sideEffects、relatedApis |
| `coverage.routeMenuMap[]` | 模块顺序参考（非执行顺序唯一依据） |
| `project-analysis.auth` | 测试账号、登录路由 |
| 已草稿化的用例 | `steps`、`produces`、`featureRef` |

---

## 3. 变量分类（通用）

| 类型 | 来源 | 编排策略 |
|------|------|----------|
| **系统变量** | `{{username}}`、`{{password}}`、`{{timestamp}}` | 不建立 dependsOn |
| **会话变量** | 登录用例 `produces: ["sessionToken"]` 或等价 | 业务用例通过 `ensure_session` 消费 |
| **业务变量** | 创建/选择步骤的 `saveAs` 或 `produces` | 须指向生产者用例 |
| **上下文变量** | 当前项目、当前租户选择 | 由「选择上下文」类用例生产 |

扫描范围：每条 `steps[]` 的 `value`、`target`、`saveAs`、`useVar`。

---

## 4. 生产者识别

登记为生产者的条件：

```
IF 用例在 happy / 主成功路径
AND (
  produces[] 非空
  OR 某 step 含 saveAs
  OR 功能类型为 create / register / import
)
THEN 将 saveAs / produces 中的变量绑定到本用例 id
```

同变量多生产者时优选：

1. 显式 `produces` 声明
2. 功能清单中 type 为 `form` / `dialog` 的创建类
3. `executionTier` 更小

---

## 5. 消费者识别与依赖补全

对每个用例：

1. 收集步骤中引用的所有业务变量（§3）
2. 对每个变量 `v`，若生产者索引存在 → `dependsOnCases` 加入生产者 id，`consumes` 加入 `v`
3. 业务用例（非登录/守卫专项）且步骤含 `ensure_session`：
   - `dependsOnCases` 应含**登录生产者**用例 id（若尚未登录则由执行器兜底，但编排仍应声明）

**守卫专项**（未登录重定向）：步骤以 `reset_session` + `navigate` 开头，tier=`session-guard`，**不**依赖登录生产者。

---

## 6. executionTier（通用分层）

| tier | 键名 | 判定规则 |
|------|------|----------|
| 0 | `login-bootstrap` | 完整登录流程且 `produces` 会话变量 |
| 1 | `session-guard` | 未登录访问受保护页、路由守卫专项 |
| 2 | `resource-create` | 新建/注册/导入成功并 `produces` 业务变量 |
| 3 | `resource-read` | 列表、筛选、详情查看 |
| 4 | `resource-update` | 编辑、保存 |
| 5 | `resource-action` | 发布、审批、导出等动作 |
| 10 | `default` | 其他 |
| 80 | `resource-delete` | 删除、批量删除 |
| 90 | `auth-destructive` | 退出登录、修改密码等 |

识别 **auth-destructive** 时读功能语义（`featureInventory.name` / 步骤文案），例如：

- 退出、登出、logout
- 修改密码、change password
- 切换账号（若会清除当前会话）

---

## 7. sessionImpact

```json
"sessionImpact": "invalidate"
```

仅用于 **happy 路径下会清除当前登录态** 的用例（§6 tier=90）。

执行器行为约定：遇到 `invalidate` 后应能重新 `ensure_session`（重新登录）。

---

## 8. 与导航路径的协作

| 维度 | 导航（10） | 编排（本文件） |
|------|------------|----------------|
| 业务用例入口 | `ensure_session` → `click_menu` | 不改为 `navigate` |
| 登录用例 | `reset_session` → `open_login` | `executionOrder` 最前 |
| 守卫用例 | 允许 `navigate` 直达 | tier=1，靠前但次于 login-bootstrap |
| 破坏性认证 | 用户菜单操作 | tier=90，`executionOrder` 最后 |

---

## 9. 拓扑排序与 executionOrder

算法同接口编排（见 `api-test-case-generate/智能编排.md` §8）：

1. `dependsOnCases` 建图
2. 同层按 `(executionTier, module, id)` 排序
3. 赋值 `executionOrder` 1…N
4. **重排 JSON 数组**与 `executionOrder` 一致

---

## 10. 输出字段

### 10.1 用例级

| 字段 | 说明 |
|------|------|
| `dependsOnCases` | 上游用例 id |
| `produces` / `consumes` | 变量产出与消费 |
| `executionTier` | §6 |
| `executionOrder` | 1…N |
| `sessionImpact` | 可选 `invalidate` |

步骤级继续支持 `saveAs` / `useVar`（与用例级 `produces`/`consumes` 一致）。

### 10.2 元信息 `orchestration`

写在首元素 meta 根级或 `coverage.orchestration`（二选一，项目内保持一致）：

```json
{
  "strategy": "smart-orchestration-v1",
  "kind": "functional",
  "totalCases": 48,
  "casesWithChainFields": 32,
  "dependenciesWired": 45,
  "producerVariables": ["sessionToken", "orderName", "orderId"],
  "loginBootstrapCaseId": "TC-FUNC-AUTH-001",
  "warnings": []
}
```

## 11. Agent 执行清单

```
- [ ] A. 从 featureInventory 标出生产者/消费者功能点（09）
- [ ] B. 确认登录生产者用例含 produces 会话变量
- [ ] C. 创建类用例：步骤 saveAs + 用例 produces 对齐
- [ ] D. 编辑/删除/筛选用例：补 dependsOnCases + consumes + useVar
- [ ] E. 标注 auth-destructive 的 sessionImpact
- [ ] F. 赋值 executionTier
- [ ] G. 拓扑排序 → executionOrder → 重排数组
- [ ] H. 写入 orchestration 元信息
- [ ] I. §12 验收
```

---

## 12. 验收要点

- [ ] 登录生产者 `executionOrder` 为 1（或 tier=0 且无前置依赖）
- [ ] 使用 `{{orderName}}` 的用例 `dependsOnCases` 含创建 order 的用例 id
- [ ] `sessionImpact: invalidate` 用例位于文件末尾（后 10%）
- [ ] 业务用例无违规 `navigate`（守卫专项除外）——仍由 10 验收
- [ ] `dependsOnCases` 引用均存在
- [ ] 每条 P0 用例 `assertions` ≥ 2（质量门槛，见 06）

---

## 13. 反模式

| 反模式 | 正确做法 |
|--------|----------|
| 每条业务用例写完整登录步骤 | `ensure_session` + 编排保证顺序 |
| 改密/登出排在创建之前 | tier=90，置后 |
| 使用 `{{orderName}}` 却无 consumes | 补全依赖 |
| 按路由表顺序直接落盘 | tier + 拓扑排序 |
| 编排替代 `click_menu` | 编排管顺序，10 管路径 |

---

## 14. 示例（通用 CRUD）

```json
{
  "id": "TC-FUNC-ORDERS-003",
  "featureRef": "FEAT-ORDERS-EDIT",
  "dependsOnCases": ["TC-FUNC-AUTH-001", "TC-FUNC-ORDERS-002"],
  "consumes": ["sessionToken", "orderName"],
  "steps": [
    { "step": 1, "action": "ensure_session" },
    { "step": 2, "action": "click_menu", "target": "订单管理" },
    { "step": 3, "action": "fill", "target": "placeholder:订单名称", "value": "{{orderName}}", "useVar": "orderName" },
    { "step": 4, "action": "click", "target": "查询" }
  ],
  "executionTier": 4,
  "executionOrder": 12
}
```

`TC-FUNC-ORDERS-002` 为新建订单用例，`saveAs: "orderName"` 与 `produces: ["orderName"]` 一致。
