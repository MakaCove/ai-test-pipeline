# 选择器策略（UI 执行通用）

> 适用 `ui-test-execute` 与 `functional-test-case-generate`。
> 目标：让 UI 用例**重跑结果稳定、可复现**，摆脱「换一次文案就飘」的脆弱定位。

---

## 1. 为什么需要策略

UI 用例的 `steps.target` 默认是用户可见文案（如「进入工作台」）。纯文案定位的问题：

- 文案改动（i18n、措辞调整）即失效
- 同文案多处出现产生歧义
- 重跑结果不稳定，无法用于回归

因此执行器（`run-functional-tests.mjs`）采用**分层定位**：高稳定策略优先，逐级兜底，并把**实际命中的策略**记录在步骤执行结果中，便于复盘哪些用例依赖脆弱定位。

---

## 2. 定位优先级（执行器内置顺序）

| 优先级 | 策略 | 触发方式 | 稳定性 |
|--------|------|----------|--------|
| 1 | **data-testid** | `target` 写成 `testid=<值>` | 最高 |
| 2 | **role + name** | 自动尝试 button/link/menuitem/tab | 高 |
| 3 | **label / placeholder** | 表单输入框 | 中–高 |
| 4 | **文案（getByText）** | 兜底 | 低 |

执行器从上到下尝试，命中即停，并记录 `strategy`（如 `role=button[name=进入工作台]`）。

---

## 3. 生成侧建议（functional-test-case-generate）

读 View/Page 源码时，**优先**为关键控件提供稳定锚点：

1. 若源码已有 `data-testid` / `data-test` / `aria-label`，`target` 直接写 `testid=<值>`。
2. 无 testid 但为标准控件（按钮、链接、输入框），写**可见文案**即可，执行器会用 role+name 命中。
3. 仅在无替代时使用纯文案，并尽量保证文案在当前页面唯一。

```json
{ "step": 3, "action": "click", "target": "testid=submit-order" }
{ "step": 3, "action": "click", "target": "提交订单" }
```

---

## 4. 回写与复盘

Markdown 报告或执行日志中每个 step 可含定位策略回写，例如：

```json
{ "step": 3, "action": "click", "target": "提交订单", "ok": true, "strategy": "role=button[name=提交订单]" }
```

- `strategy` 为 `text=...` 的用例属**脆弱定位**，回归不稳定时优先排查。
- 建议在被测项目逐步为高频控件补 `data-testid`，把脆弱用例迁移到 testid 策略。

---

## 5. 反模式

| 反模式 | 正确做法 |
|--------|----------|
| 全部用 CSS/XPath 绝对路径 | 用 role+name 或 testid，语义稳定 |
| 文案写得过长含动态内容 | 取稳定子串或改用 testid |
| 多处同文案不加限定 | 加 testid 或在生成侧标注唯一性 |
